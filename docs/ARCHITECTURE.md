# Architecture — how 9Router runs on Android

## The core problem

9Router is a **Node.js / Next.js 16** server. It is *not* a static binary and it is
*not* written for Android. The naive assumption — that you can copy a desktop
`.next` folder or an npm package straight into an APK — is wrong for two reasons:

1. Node.js itself does not run from an APK; the `node` executable is compiled for
   the host OS/libc (glibc) and does not match Android's **Bionic** libc.
2. A Next.js SSR app needs a build (`next build`) and a set of runtime deps; it
   isn't a lone JS file.

So the correct architecture is **"embedded Node.js runtime + pre-built Next.js
standalone bundle."**

## Why this is the right approach for 9Router

We inspected the upstream repo (commit `eb712ca821f0ba6bc41043fbd14494c5af5daba5`,
v0.5.69) and confirmed it is a good fit for embedding:

| Upstream fact | Why it matters |
|---------------|----------------|
| `next.config.mjs` sets `output: "standalone"` | `next build` produces `.next/standalone/` containing `server.js`, a **slimmed `node_modules/`**, and a build-sensitive path layout — perfect to ship as-is. |
| Entry point `custom-server.js` | Express + `http-proxy-middleware` wrapper; when run beside `server.js` it `require`s the standalone server. No extra CLI needed. |
| DB: `sql.js` (WASM) as fallback, `better-sqlite3` optional | `better-sqlite3` is a native module; but `sql.js` is pure WASM and is the **runtime fallback**, so **no native compilation is required on Android**. |
| `serverExternalPackages: ["better-sqlite3","sql.js","node:sqlite","bun:sqlite","open"]` | These are traced into the standalone `node_modules`; no recompile needed. |
| Port/host from env | `server.js` reads `PORT` and `HOSTNAME`, so we control binding without patching source. |

The only Android-specific artifact is the **`node` binary**.

## Compared alternatives (and why rejected)

| Option | Verdict |
|--------|---------|
| **Termux runtime integration** | Usable, but requires bundling/launching Termux and its package repo; heavier, more fragile, and arguably still "operating Termux" under the hood. Rejected. |
| **Native Android server wrapper** (pure Kotlin rewrite) | Would mean rewriting 9Router's routing/provider logic — explicitly disallowed ("do not fork or rewrite"). Rejected. |
| **Bun/Deno on Android** | Not as well-supported / not present; 9Router targets Node and uses `node:` built-ins + `undici`. Rejected. |
| **Embedded Node.js + standalone bundle** | ✅ Chosen. No root, no downstream tooling, keeps upstream intact. |

## Runtime layout

After `scripts/package_runtime.sh`, `app/src/main/assets/9router-runtime/` looks like:

```
assets/9router-runtime/
  bin/node                       # Node.js, aarch64-linux-android
  lib/*.so                       # shared libs node needs on Android (libc++_shared.so, etc.)
  bundle/
    custom-server.js             # upstream wrapper
    server.js                    # Next.js standalone server
    .next/static/                # built static assets
    public/                      # upstream public assets
    node_modules/                # slimmed, traced runtime deps
    package.json
  runtime-manifest.json          # upstream commit + node version
```

At first CONNECT the app copies this tree into `filesDir/9router/runtime/` and
makes `node` executable (`RouterRuntime`). No root, no `install`.

## Per-instance data & secrets

`InstanceManager` owns `filesDir/9router/data/inst-<timestamp>/`:

```
inst-<timestamp>/
  .env         # generated at runtime (JWT_SECRET, INITIAL_PASSWORD, DATA_DIR, PORT, ...)
  data/        # 9Router's DATA_DIR (sql.js WASM database)
  logs/        # reserved
```

Secrets are generated by `SecretGenerator` (`java.security.SecureRandom`) and
stored through `SecureStorage` (Android Keystore-backed
`EncryptedSharedPreferences`). Nothing is committed, nothing is logged
(`AppLogger.sanitize` strips credentials from all log output).

A representative `.env` written for the instance:

```
JWT_SECRET="<random>"
INITIAL_PASSWORD="<random>"
API_KEY_SECRET="<random>"
MACHINE_ID_SALT="<random>"
DATA_DIR="<instance>/data"
PORT="20128"
HOSTNAME="127.0.0.1"            # or 0.0.0.0 in LAN mode
NODE_ENV="production"
BASE_URL="http://127.0.0.1:20128"
NEXT_PUBLIC_BASE_URL="http://127.0.0.1:20128"
REQUIRE_API_KEY="false"
ANDROID_ROOT="/system"
HOME="<instance>"
TMPDIR="<instance>"
LD_LIBRARY_PATH="<runtime>/lib:…"
```

`custom-server.js` requires `server.js` (present in the bundle); `server.js` reads
`PORT` and `HOSTNAME` from env. We pass `--port` too (harmless for the standalone
path; used only by the `next start` fallback).

## Process lifecycle

```
CONNECT
  └─ RouterForegroundService.start()
       └─ RouterManager.start()
            ├─ RouterRuntime.extractIfNeeded()     → filesDir/9router/runtime/
            ├─ InstanceManager.buildConfig()        → .env + InstanceConfig
            ├─ RouterProcess.start()                → spawn `node custom-server.js`
            ├─ HealthChecker.waitUntilHealthy(/v1/models)
            └─ state = CONNECTED → notification "Local API: …:PORT"
DISCONNECT
  └─ RouterManager.stop()
       ├─ RouterProcess.stop()  → SIGTERM, then SIGKILL after grace
       └─ state = STOPPED → service stops foreground
Crash while CONNECT on
  └─ RouterProcess onExit → RouterManager.handleExit
       ├─ autoRestartEnabled? attempts < max? (exponential backoff 1s·2^n)
       └─ restart → health check → notification update
```

Auto-recovery is bounded by `maxRestartAttempts` (default 5), so there is never an
uncontrolled restart loop.

## Upstream compatibility

- **Upstream commit pinned:** `eb712ca821f0ba6bc41043fbd14494c5af5daba5`
  (`v0.5.69`, tag `2026-09-05`). See `scripts/package_runtime.sh`
  (`UPSTREAM_COMMIT`) and `runtime-manifest.json`.
- **Patches to upstream:** none. We do not modify routing/provider/auth logic.
  The only integration is a thin host-side packaging step, plus a handful of
  Android-runtime **environment variables** applied by the app (documented above).
- **Android-specific modifications:** only in the wrapper (Kotlin) — environment
  wiring, extracted runtime, foreground service, notification, WebView dashboard.

## Node binary for Android

The one non-trivial dependency is the Node executable. It must be a build for
**`aarch64-linux-android`** (Bionic). Sources:

- **nodejs-mobile** — official Node.js for Android (`libnode.so` + node wrapper).
- A **Termux** `nodejs` package binary for arm64, or any static/dynamic Node build
  targetting Android ARM64.

> ⚠️ A generic Node download from nodejs.org (`node-vX-linux-arm64.tar.xz`) is
> linked against **glibc** and will **not** run on Android's Bionic. Use a build
> for `aarch64-linux-android`.

The script verifies the binary is an aarch64 ELF (`file`), copies it to
`bin/node`, and copies any companion `.so` files into `lib/`. The app sets
`LD_LIBRARY_PATH` to that `lib/` dir.

## Known limitations

- **ARM64 only.** `x86_64` / `armeabi-v7a` builds are not shipped by default.
- **Node binary not committed** (it's large and not universal). It must be added
  by `scripts/package_runtime.sh` before `assemble*`; see `.gitignore`.
- **sql.js WASM:** the standalone build traces `sql.js`, but the `.wasm` file must
  be resolvable at runtime. If it can't load, 9Router's DB falls back / errors —
  see TROUBLESHOOTING.
- **Dashboard is heavy** (Monaco editor, recharts). It can be slow on low-end
  devices; use the "open in external browser" setting when needed.
- **Background/battery:** a foreground service can still be killed under extreme
  battery saver. `START_STICKY` + app auto-resume (in `NineRouterApp`) recovers on
  the next launch.
- **`/v1` API-key requirement** defaults to `false` (matches upstream `.env.example`).
  A generated endpoint key is shown in the UI; if you set `REQUIRE_API_KEY=true`,
  clients must present it.
- **Request counter** is best-effort (parsed from server output), not an exact
  metric.
- **LAN mode** binds `0.0.0.0`; other devices could reach the endpoint. Use only on
  trusted networks and keep API-key protection on. The app warns on enable.

## Tests

- The Android app has unit/instrumentation stubs in `app/src/test` and
  `app/src/androidTest`; add LogStore/SecretGenerator unit tests as needed.
- To validate the embedded server on a Linux x64 host, run the bundle directly:

  ```bash
  (cd app/src/main/assets/9router-runtime/bundle && PORT=20128 HOSTNAME=127.0.0.1 node custom-server.js)
  ```
